## What

DEP-4 has `.metal` sources compiled by the Xcode build system into the target's resource bundle and loaded with `makeDefaultLibrary(bundle: .module)`. The package instead copies the shader sources into the bundle as they are (`resources: [.copy("Shaders")]`) and compiles them with `MTLDevice.makeLibrary(source:options:)` when a `MetalContext` is created, off the main thread.

## Why

The build machine has no offline Metal toolchain (`xcrun metal` reports that the Metal Toolchain component is not installed, and installing it is a download the owner has not approved). DEP-4 is marked as an assumption to be confirmed by WP-601; it does not hold here. Compiling from source costs some milliseconds once per context and keeps the package buildable on any Xcode installation.

## Evidence

`xcrun -sdk iphonesimulator metal --version` on the host. The Metal tests build a library from the copied sources on the simulator.

## Sections affected

§4.2 (DEP-4), §8.2.

## Owner's decision / outcome (2026-11-28)

**Withdrawn.** The deviation is no longer needed, and the package follows DEP-4 as written.

- **2026-11-21.** The owner approved the Metal Toolchain component on the build machine. That removes the reason given under Why. The component (Metal Toolchain 27.1.266.1, `metal` 32023.921) is installed.
- **2026-11-28.** Brief 76 brought the package to DEP-4 (report `Docs/Process/reports/impl-WP-601-offline-shaders.md`):
  - The manifest no longer copies `Shaders/`. The build compiles each `.metal` file and links them into `default.metallib` in the bundle of `ZTronDSPMetal`. No shader source travels in the bundle.
  - The one declaration two shader files share, `ZTDScreenVertex`, is now in `Shaders/Common.h`, which the four files that need it include.
  - `MetalContext` loads that library with `makeDefaultLibrary(bundle: .module)`. A bundle without a library that loads, or a library that lacks a function a pipeline asks for, is `backendUnavailable`, never a trap.
  - No `makeLibrary(source:` remains under `Sources/`. Part 4 of `Scripts/lint-bans.sh` reports one under the rule DEP-4.
  - `Scripts/xc.sh build` and `test` stop without the component, with one line that names `xcodebuild -downloadComponent MetalToolchain` (status 64).
  - Every CI job that builds downloads the component before its first gate. Gate 1 treats the Metal compiler's warnings as errors.
  - The public API is unchanged (`Scripts/api-digest.sh --check`).

### What was measured

- **Compile options.**
  - Math mode: fast in both paths, at run time (`MTLCompileOptions()`, which is what `options: nil` gives) and in the build (`-fmetal-math-mode=fast`, `-fmetal-math-fp32-functions=fast`). So is the precision of the single-precision functions.
  - Neither path defines a preprocessor macro, preserves invariance or emits debug information.
  - The language version differs: MSL 4.0 at run time, for a binary whose deployment target is iOS 15.0, against MSL 2.4 in the build, which takes it from the deployment target (no `-std`).
    - The manifest has no setting for it.
    - MSL 4.0 cannot serve the package's floor. Its AIR (version 2.8) is linked only for a deployment target of iOS 26: for iOS 15.0 the linker ignores the file ("file AIR version (2.8) is bigger than the one of the target being linked (2.4)"), and for iOS 18.0 the limit is 2.7.
    - The shaders use nothing that depends on the version, nor the macros that differ between the two paths (`__METAL_VERSION__`, `__METAL_IOS__`).
- **Numbers.** The 32 numerical lines the GPU tests print are the same, character for character, before and after, in Debug and in Release: the warp tables of the frequency scales, the relative and decibel errors of the heat-map texture, the half-float sampler probe, the GPU median against its oracle, the PSNR and largest difference of the 23 golden heat-map and waveform images, and the WP-612 medians. No tolerance changed.
- **Creating the shared context** (`MetalContext.shared()`, timed by `theSharedContextWorksOnTheSimulator()` alone, iOS 27.0 simulator, one launch each):

  | Build | Before (run-time compilation), ms | After (`default.metallib`), ms |
  |---|---|---|
  | Release | 27.9, 20.4, 25.0, 21.6, 18.5 (median 21.6) | 437.2, 19.3, 19.0, 24.9, 24.1 (median 24.1; of the last four 21.7) |
  | Debug | 22.3, 23.9, 26.4 (median 23.9) | 22.7, 22.7, 20.4 (median 22.7) |

  The first launch after the build took 437.2 ms because the simulator's Metal cache had not seen the new library: the device turned its AIR into GPU code once. Before, that cache already held what the same source had given for days. With both Metal caches of the test process emptied before each launch, the front end's and the GPU code's, in Release: before 6891.3, 722.4 and 715.8 ms (the first also rebuilt the front end's module cache), after 851.3, 259.3 and 392.5 ms; medians 722.4 and 392.5 ms.

  In the run of every test target, among the other tests, the first call took 157.6 ms before and 83.7 ms after in Debug, 61.5 and 57.2 ms in Release.
- **Tests.** Every test target in Debug and in Release on the iOS 27.0 simulator: 2839 test cases before, 2840 after. The Metal target lost the two tests of run-time compilation and gained three: the bundle holds `default.metallib` and no shader source; the library holds exactly the functions the pipelines ask for, compared both ways; a bundle without the library, or a library without a function, is `backendUnavailable`. Nothing failed before or after, apart from the three expected failures of the testing target. The Metal and UI targets twice more on 27.0 in each configuration: all passed. On iOS 18.6 and 17.5, in each configuration, the Metal target passed before and after: the library built for a deployment target of iOS 15.0 loads on the oldest runtime installed here. The UI target failed the same tests before and after, three on 18.6 and six on 17.5, all of them findings of the tree as found. The gallery's hosted suites passed on 27.0 and 18.6. On 17.5 `aRotationThereAndBack()` failed before and after, at 1.29 and 1.05 px against its bound of 1 px. The external parity suite and the gates are in the report (section 3).
