## What

A new rule beside RT-2 and RT-7:

- **RT-10** Swift code in the hot directories (`Kernels/`, `Nodes/`, `Engine/Run/`) and in the toolkit's native loops is
  written with `while` loops, never `for … in`, and without `SIMD8`-style generic vector types, so that the steady state
  is allocation-free in an unoptimised build as well as an optimised one. Lint part 2 bans `for … in` in the hot
  directories.
- The run-time audit of RT-7 (layer 3) passes in the Debug configuration, which is the default of every test run, and
  is run again in Release by gate 5.
- The "8-lane SIMD" reductions of §7.4 are eight scalar accumulators, which the optimiser turns into vector registers.

## Why

Xcode builds a package in the configuration of the app that uses it, so a developer running a Debug build of an app
gets ZTronDSP at `-Onone`. A real-time promise that holds only at `-O` would not hold on the device on the developer's
desk.

## Evidence

Measured with the allocation probe on Swift 6.4 (Xcode 27.0), iOS 27.0 simulator, in a library module and in test code:

| Construct, 100 iterations or 1 000 calls | `-Onone` | `-O` |
|---|---|---|
| `for i in 0 ..< n { p[i] *= 0.5 }` | 100 allocations of 40 bytes: one per iteration | 0 |
| `for i in buffer.indices { … }` | 100 allocations | 0 |
| `var i = 0; while i < n { p[i] *= 0.5; i += 1 }` | 0 | 0 |
| a class method or an existential method called in a `while` loop | 0 | 0 |
| `SIMD8<Float>` accumulate over a pointer (`loadUnaligned`, `+=`, `.sum()`) | about 16 allocations of 40 bytes per call | 0 |
| eight scalar accumulators | 0 | 0 |

Also measured: `vDSP_vclip`, `vDSP_vthr`, `vDSP_vmax` and `vDSP_vmin` pass a NaN through, `vDSP_vthres` writes 0 for
one. The decibel conversions therefore threshold with `vDSP_vthres` first (NUM-1).
