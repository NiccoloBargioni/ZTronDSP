## Lens checklist (§11.5)

- **R — real-time safety and performance.**

- RT-2 / RT-5: `append` is one `memcpy`, two atomic stores and one atomic add into storage allocated on the control context; it takes no lock and wakes no one (`ColumnStore.swift:342-354`). Liveness is published by the control context and the main thread, never by the writer (`BindingPump.swift:10-70`).
- RT-4: readers share a lock with the control context only; `generation` is one atomic load. The validation of a read is the subject of finding 1.
- RT-3: a replaced layout goes through a `Handoff` and is freed by the control context; the writer's local reference to it can be the last one (same shape as WP-319a, finding 1; `ColumnStore.swift:325-337`).
- No benchmark is recorded for the feed by itself.

**Finding 1, to reproduce or resolve.** Probe (4 s per case, one writer thread that never rests, three reader threads):

```swift
let feed = HeatmapFeed(history: 1); let rows = 48
try feed.claim(axis: .indices(count: rows), environment: DSPEnvironment(), domain: .chroma, format: .real(count: rows))
// writer:  column.update(repeating: v); feed.write(FrameView(real: column, index: 0, time: Double(v))); v += 1
// readers: feed.read(&cursor, into: values, times: times); every column returned holds one value, and its time is that value
```

| Store | Debug | Release |
|---|---|---|
| `HeatmapFeed(history: 1)` | 745 torn of 3.0 M columns read | 14 273 of 6.6 M; second run 9 183 of 6.4 M |
| `HeatmapFeed(history: 2)` | 0 | 1 736 of 11.7 M; 1 229 of 7.7 M |
| `HeatmapFeed(history: 4)` | 0 | 26 of 11.3 M; 1 of 9.4 M |
| `HeatmapFeed(history: 32)` | not run | 0 of one run |
| `ResultSlot(kind: .vector)`, `readVector()` | 2 of 0.57 M | 72 of 11.6 M |

Control experiment: with `atomic_thread_fence(memory_order_seq_cst)` after the writer's first store
(`ColumnStore.swift:345`, `ResultSlot.swift:53`) and before the reader's validating load (`ColumnStore.swift:216`,
`ResultSlot.swift:80`), the same runs in Release gave 0 torn in every case. Cause: the counters are loaded with
`memory_order_acquire` and stored with `memory_order_release` (`ztd_atomic.c:22-28`), LDAR and STLR on arm64; neither orders
the reader's copy before its validating load, nor the writer's copy after its first store, so a reader can validate
against a count that is older than the data it copied. `FeatureStream` uses the same scheme (`FeatureStream.swift:123-159,
213-238`). To resolve: a full barrier in those two places (the classic sequence-lock recipe), and a stress with a history of 1.

**Finding 2, to reproduce or resolve.** Probe (the same in Debug and Release):

```swift
let rig = Rig(); let feed = HeatmapFeed(history: 16, minimumHistory: 4)
let session = try await rig.engine.attach(
    Pipeline().tap { $0.testFramer(frame: 64, hop: 64).testMagnitude().emit(to: feed) }, to: rig.source)
try session.start(); rig.feed(TestSignal.whiteNoise(count: 64 * 12, seed: 5)); session.stop()
try rig.engine.core.control.sync { rig.engine.core.respond(to: .critical) }
#expect(feed.snapshot().columnCount == 4)        // fails: 0, and feed.columnCount == 0
```

Cause: `trim` (`ColumnStore.swift:290-300`) publishes an empty layout and makes it the readers' layout at once; the newest
columns are copied into it by the writer when it next writes (`ColumnStore.swift:325-335`). A feed whose session is stopped,
finished or interrupted has no writer, so it shows nothing from then on. The package's test writes one more block before it
looks. To resolve: copy on the control context when no writer runs, or keep the old layout for readers until the writer
has moved.

**Finding 3, to reproduce or resolve.** To resolve: checked multiplication and a typed error from `configure`.
