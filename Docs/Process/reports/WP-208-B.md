## Lens checklist (§11.5)

- **R — real-time safety and performance.**
  - `process`, `command` and `reset` are `ZTD_NONBLOCKING`, defined in a target built with function-effect errors (the check bites: `malloc(16)` written into `ztd_gain_process` stops the package build: "function with 'nonblocking' attribute must not call non-'nonblocking' function 'malloc' [-Werror,-Wfunction-effects]"). Read against RT-2: no allocation, no lock, no system call, no logging; every loop is bounded by the frames, the channels or a size fixed at creation.
  - Allocation audit: `BiquadCoefficientUpdateTests.processingAndCoefficientUpdatesAreAllocationFree(bound:)` (the kernel's one audit, in the suite of WP-209; 1 000 blocks of 7 and 512 frames, 50 updates, a reset) passes in Debug and Release for both implementations. It bites: with an allocation the compiler cannot see (a call, from the hot function, to a helper in another file that does `malloc` and `free` and is declared `nonblocking`, as an allow-list entry is; tried in Debug and in Release, with the same counts) in both `process` functions and both `command` functions it reports 1 050 allocations per implementation.
  - The setup is created in `ztd_biquad_create` only (`vDSP_biquad_CreateSetup`, behind the creation seam) and destroyed in `destroy`; the delay values, and a 1 024-frame aligned buffer, are allocated there too.
  - SEL-3: two `process` functions, one stored at creation; no size test on the hot path.
  - Cost O(sections) per sample, plus O(channels · sections) per block for the state flush. Benchmark recorded: `kernel.biquad.accelerate.4-sections.4` 37.0 ns, `.512` 1923 ns; `kernel.biquad.native.4-sections.4` 45.0 ns, `.512` 5733 ns. (On this host the C loop does not lead even at 4 frames; the crossover of §7.4 is WP-611's to settle.)
