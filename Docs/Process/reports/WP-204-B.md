## Lens checklist (§11.5)

- **A — API, architecture, platform.**
  - Shape against §5.11.1: `ztd_kernel_t` has the fields of the specification in its order — `process` at offset 0, `command` 8, `reset` 16, `destroy` 24, `state` 32, `latency_frames` 40, `settling_frames` 44; 48 bytes (read from Swift with `MemoryLayout`). The first three function pointers are `ZTD_NONBLOCKING`, `destroy` is not. `ZTD_ABI_VERSION` is 1.
  - The one difference, `process` returning `uint32_t` (frames written), is CR-004, which describes the code exactly; its evidence test `PlanTests.aRateChangeInsideAPlanCarriesItsFrameCountOn` exists and passes.
  - `ztd_plan_t` is opaque; `ztd_plan_run` is non-blocking and makes one indirect call per kernel per block through a flat table (§5.5.2), with two scratch tables the plan owns, allocated when it is created. `in` and `out` of a kernel never alias (read for one kernel, several, a range and a switched stage).
  - Threading contract stated at the top of ztd_kernel.h and by section in ztd_plan.h (control context / analysis thread). No configuration object; names carry the `ztd_` prefix throughout. Headers compile as C11 and C++17 standing alone. The digest `Docs/API/CZTronDSP.txt` equals the build.
  - `ztd_command_t` (48 bytes) is not given a shape by the specification; it is documented in ztd_kernel.h.
