- **Precision.** `Float` throughout the node: class sums, the threshold, the norm, the division. Right for the size of the sums, not for their range: a class collects B/12 bins in each octave (21 at the defaults), so a sum is within about 21·ε of its exact value, and the cosines above measure 0.99990 at worst. ## Change requests filed (FIX-4)

**CR-A3 (proposed): the pitch class of bin 0.**

- *What.* §6.8 says "Bin k belongs to pitch class round(12·k / B) mod 12". Read literally, bin 0 is class 0, which the feed labels C, whatever note the transform starts on. `ChromaFold` (WP-524) puts bin 0 on the class of the semitone nearest to f_min, C being 0: class(k) = (c₀ + round(12·k / B)) mod 12 with c₀ = round(69 + 12·log₂(f_min / 440)) mod 12, and documents it ("a transform that starts on a C starts on class 0 and one that starts on an A on class 9", `ChromaFold.swift:100-103`).
- *Why.* The rows of a chroma feed are "The twelve pitch classes, C first" (`FeedAxis.pitchClasses`, VC-5), and §6.8's acceptance asks that the strongest pitch class be correct. For a transform from A2 the literal reading would label every A as C; the code's reading gives the right class for all 72 tones (this report). With the default f_min, C1, the two coincide, which is why the sentence reads as it does; the next verifier should not have to infer the anchor.
- *Proposed wording* (§6.8, `ChromaFold`): "Bin k belongs to pitch class (c₀ + round(12·k / B)) mod 12, where c₀ is the class of the semitone nearest to f_min, C being 0; so each class collects the B/12 bins nearest to its semitone in every octave, and the classes are C first whatever note the transform starts on. Tuning has already moved the bins and does not move the classes."
- *Evidence.* `VerifierA/out/chroma_classes_from_a.json`; `ref-results-alignment-pseudo-chroma.json`, key `524.classes-from-A`; `ChromaTests.aBinBelongsToTheClassOfTheSemitoneNearestToIt()`.
- *Sections affected.* §6.8 (`ChromaFold`); none of the code.
