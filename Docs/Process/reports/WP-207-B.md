## Lens checklist (§11.5)

- **R — real-time safety and performance.**
  - `process`, `command` and `reset` are `ZTD_NONBLOCKING`, defined in a target built with function-effect errors (the check bites: `malloc(16)` written into `ztd_gain_process` stops the package build: "function with 'nonblocking' attribute must not call non-'nonblocking' function 'malloc' [-Werror,-Wfunction-effects]"). Read against RT-2: no allocation, no lock, no system call, no logging; every loop is bounded by the frames, the channels or a size fixed at creation.
  - Allocation audit: `GainKernelTests.processingAndCommandsAreAllocationFree(bound:)` (1 000 blocks, ramped and constant paths, 25 commands) passes in Debug and Release for both implementations. It bites: with an allocation the compiler cannot see (a call, from the hot function, to a helper in another file that does `malloc` and `free` and is declared `nonblocking`, as an allow-list entry is; tried in Debug and in Release, with the same counts) in `ztd_gain_process` and `ztd_gain_command` it reports 1 025 allocations per implementation (1 000 blocks + 25 commands).
  - Everything is allocated in `ztd_gain_create` (state, per-channel table, a 512-frame ramp buffer). No setup. No copy of the signal: a ramp is rendered into the kernel's buffer and multiplied in.
  - SEL-3: the implementation is two function pointers stored at creation; the hot path has no size test and no branch on the choice. CR-013 item 3 (no `vDSP_vrampmul`; the ramp rendered and `vDSP_vmul`) describes the code as it is.
  - Cost O(frames · channels). Benchmark recorded: `kernel.gain.native.64` 13.9 ns, `.native.512` 57.3 ns, `kernel.gain.accelerate.64` 14.9 ns, `.accelerate.512` 55.6 ns (Release, serial run on a busy machine).
