| B-9 | A result is wrong: the pointer form of subsampling does not compute what it is documented to be the pointer form of | Sources/ZTronDSPCore/Toolkit/RateChange.swift:44 against :2 and :6 | `subsampled(_:by:phase:)` wraps a phase outside `0 ..< factor` into it, as documented (`((phase % factor) + factor) % factor`, :6); `subsample(_:count:by:phase:into:)`, documented as "the pointer form of `subsampled(_:by:phase:)`", clamps it instead (`min(max(phase, 0), factor - 1)`, :44). On the samples 0 … 9 with factors 2, 3 and 4 and phases −5, −4, −1, 0, 1, factor − 1, factor, factor + 1, 2·factor + 1, 9 and 12, 19 of the 33 calls (18 of 32 distinct pairs) give different samples: factor 2, phase −1 keeps 1, 3, 5, 7, 9 in the array form and 0, 2, 4, 6, 8 in the pointer form; factor 3, phase 4 keeps 1, 4, 7 and 2, 5, 8 (`wp117.outOfRangePhase.disagreements`). A stage that passes its own phase, or any phase it did not get back from the previous call, gets other samples than the array form gives. Debug and Release. Reproduction: `ZTD_DEVICE=ztdsp-27-vm1b Scripts/xc.sh test "ZTronDSPCoreTests/VerifierBProbes/wp117_aPhaseOutsideTheFactorAgreesBetweenTheForms()"` (1 issue: 19 disagreements). Resolution: wrap the phase in the pointer form as the array form does, and add phases outside the range to `thePointerFormsMatchTheArrayFormsAcrossIrregularBlocks`. | Blocking |
| B-10 | §9.3 "No `fatalError` or `precondition` is reachable from public API through invalid input"; RT-2 and memory safety of a function "callable on the analysis thread" | Sources/ZTronDSPCore/Toolkit/RateChange.swift:6 (array form), :44-51 (pointer form), :37 (the documented room) | A factor near `Int.max` is a valid `Int` with a well-defined result (one sample, or none). The array form computes `(phase % factor) + factor`, which overflows: `subsampled(x, by: Int.max, phase: 1)` stops the process (crash probe `subsampledHugeFactor`: marker "started", exit 65, Debug and Release). The pointer form adds the factor with wrapping arithmetic (`index &+= factor`), so the index wraps to a negative value and the loop goes on: `subsample(source, count: 10, by: Int.max, phase: 5, into:)` writes 7 samples, 5, 4, 3, 2, 1, 0 and the sentinel 99 placed before the source, so it reads `source[-1]` and writes 7 samples where its documented room, `(count + factor − 1) / factor`, is 1 (the formula itself overflows there); next phase 9 223 372 036 854 775 796 (`wp117_aFactorNearIntMaxStaysInTheRoomItAsksFor`: 1 issue; crash probe `subsamplePointerHugeFactor`: "written 7", Debug and Release). Reproduction: `ZTD_DEVICE=ztdsp-27-vm1b VerifierB/scripts/crash-probes.sh Debug subsampledHugeFactor:subsampledHugeFactor subsamplePointerHugeFactor:subsamplePointerHugeFactor` (and `Release`); `ZTD_DEVICE=ztdsp-27-vm1b Scripts/xc.sh test "ZTronDSPCoreTests/VerifierBProbes/wp117_aFactorNearIntMaxStaysInTheRoomItAsksFor()"`. Resolution: wrap the phase without overflow (`let r = phase % factor; r < 0 ? r + factor : r`), advance the pointer form's index with `addingReportingOverflow` and stop when it would pass `count` (the next phase is then `(index − count) + factor`, which cannot overflow), state the room in a form that cannot overflow, and add a huge factor to the tests. | Blocking |
| B-14 | RT-7, layer 2: "`@_noAllocation @_noLocks` on pure-Swift leaf loops, behind the build setting `ZTRONDSP_PERF_ANNOTATIONS`" | Sources/ZTronDSPCore/Toolkit/RateChange.swift:39-40 (`subsample`), :56-57 (`upsample`); the same finding for WP-119 at Ramp.swift:90-91, :103-104, :114-115 | `subsample` and `upsample` are pure-Swift leaf loops (no call inside, documented "callable on the analysis thread") and carry no attribute: `grep -c ZTRONDSP_PERF_ANNOTATIONS` gives 0 for RateChange.swift and Ramp.swift and 15 for Vector.swift, whose loops all have them. The attributes fit: with them added behind the setting, `Scripts/check-perf-annotations.sh` builds the package with the setting on and passes (`.build/vb2/trial-perf-annotations.out`, exit 0; the trial build also held two one-line `AlignedBuffer` mutations of the same stage, which touch neither file); the files were then restored and compared byte for byte ("SOURCES-BYTE-FOR-BYTE-PRISTINE", `.build/vb2/trial-restore.out`). Reproduction: `grep -c ZTRONDSP_PERF_ANNOTATIONS Sources/ZTronDSPCore/Toolkit/RateChange.swift Sources/ZTronDSPCore/Toolkit/Ramp.swift Sources/ZTronDSPCore/Toolkit/Vector.swift`; `python3 VerifierB/scripts/annotate-trial.py apply`, `ZTD_DEVICE=ztdsp-27-vm1b TMPDIR="$PWD/.build/tmp" Scripts/check-perf-annotations.sh`, `python3 VerifierB/scripts/annotate-trial.py restore`. Resolution: put the attributes on these five functions, behind the setting, as Vector.swift does. | Blocking |
| B-26 | §9.3; the documentation of a limit | Sources/ZTronDSPCore/Toolkit/RateChange.swift:18-24 | `upsampled([Float](repeating: 1, count: 4), by: Int.max / 2)` stops the process at `samples.count * factor` (crash probe `upsampledHugeFactor`, Debug and Release). No result of that length can exist and the function has no error channel, so a stop is the only outcome open to it, as for `Array(repeating:count:)`; the documentation does not say so. Resolution: state that `count · factor` must fit in memory, or clamp. | Non-blocking |
