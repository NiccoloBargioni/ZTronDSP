# Release 0.1.0 — checklist (WP-906)

What has to hold before the owner tags 0.1.0. Every line names the command that proves it and the
last line that command prints when it holds. `Scripts/release-check.sh` runs, in this order, every
line that one machine can run, and ends each in one result line: `PASS`, `FAIL`, or `OPEN` with the
reason (`device`, `owner`, `not installed`). The lines it cannot prove here (the device runs, the
owner's decisions) it reads from the records that the people who close them keep.

§12 gives the acceptance of WP-906 as "every gate of §10.3 green"; the lines after the nine gates are
what §7.3, §10.2, §11.8, §12 and §13.1 add to a release.

## How to run it

```sh
TMPDIR="$PWD/.build/tmp" Scripts/release-check.sh                # every item; exit 0 only when every item passed
TMPDIR="$PWD/.build/tmp" Scripts/release-check.sh --allow-open   # exit 0 when no item failed, though some are open
Scripts/release-check.sh --list                                   # each item and its command; runs nothing
```

- The first run, on 2026-11-22 on an Apple M3 with 24 GiB, took 2 h 01 min: gate 5 70 min (four
  simulators, the Release audit, the Thread Sanitizer), the gallery's UI tests 24 min, the scripts'
  self-tests 14 min. It left about 6 GB of derived data under `.build/` (`ci`, `ci-strict`,
  `ci-gallery`, `ci-gallery-release`, `ci-tsan`, `docs`, `xcode-perf`, `xcode-effects`), and the free
  space of the disk fell from about 52 to 41 GiB while it ran (the disk is shared with other work).
  Start with 20 GiB free: before each command the
  script reads the free space of the disk, and below 6 GiB (`ZTD_RELEASE_MIN_FREE_GIB`) it starts
  nothing more.
- Each command's output is kept in `.build/release-check/<date>-<time>/NN-<item>.log`, and the
  result lines in `summary.txt` beside them.
- Run it on the commit to be tagged, with nothing uncommitted: the item `clean-tree` fails otherwise.
- The register audit is read for the release month (`ZTD_RELEASE_MONTH`, default this month):
  `Docs/Numerics/register-audit-YYYY-MM.md`, which WP-905 writes before every release (§7.3).

Tick a line (☐ → ☑) when its command printed the expected line on the commit to be tagged, or when
its record is in place.

`release-check.sh` reads each gate from its line in ci.sh's summary. A gate that ci.sh skipped, in
whole or in part, is `OPEN (not installed)` when the skip says a PLAT-3 runtime or Octave is not
installed, `OPEN (owner)` when gate 8 found no baseline for the runner (the owner pins the runner and
commits its baselines), and `FAIL` for any other skip, which this machine could close. `run-all.sh`
and `golden.sh --reproduce` exit 0 when they skipped something; their skips are read the same way.
COV-3 (the changed files of a package) is checked per package, not here.

## 5. Version and metadata

`Package.swift` carries no version: a Swift package is versioned by its git tag. What 0.1.0 needs:

| ✓ | Item | What it proves | Command | Expected result line |
|---|---|---|---|---|
| ☐ | `changelog` | `CHANGELOG.md` has the entry of 0.1.0, dated: `## [0.1.0] - YYYY-MM-DD` | read from `CHANGELOG.md` | `PASS changelog CHANGELOG.md: ## [0.1.0] - <date>` |
| ☐ | `readme` | A README, if there is one, shows the install snippet of 0.1.0: `.package(url: …, from: "0.1.0")` | read from `README.md` | `PASS readme there is no README, so no install snippet names a version` |
| ☐ | `clean-tree` | The tree is HEAD, with nothing uncommitted, from the start of the run to its end: what was checked is the commit that will be tagged | `git status --porcelain`, `git rev-parse HEAD` | `PASS clean-tree the tree was HEAD <sha> throughout, with nothing uncommitted` |
| ☐ | `tag` | No tag 0.1.0 names another commit | `git rev-parse refs/tags/0.1.0` | `PASS tag 0.1.0 is not tagged yet: the tag goes on HEAD <sha> once this run passes, and not before` |

Releasing, once every line above is ticked: the owner dates the entry of `CHANGELOG.md`, commits it,
runs `Scripts/release-check.sh` once more on that commit (it exits 0 without `--allow-open`), and tags
that commit: `git tag -a 0.1.0 -m "ZTronDSP 0.1.0"`, then `git push origin 0.1.0`. No agent tags,
commits or pushes.

## 6. Not run by release-check.sh

- The workflow's own strict run: dispatch `.github/workflows/ci.yml` by hand with `strict` (and
  `gallery_ui`) on the commit to be tagged. It runs the gates on GitHub's runners, gate 5 once per
  runtime, and gate 8 only where the repository variable `ZTD_BENCHMARK_RUNNER` names the pinned
  runner; a strict run without it fails.
